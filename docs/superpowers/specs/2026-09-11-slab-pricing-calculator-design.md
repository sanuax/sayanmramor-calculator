# Дизайн: калькулятор на основе реальных слэбов veneziastone.com

Дата: 2026-09-11

## Контекст и цель

Текущий `sayanmramor-calculator.html` — статический калькулятор с
захардкоженными диапазонами цен «от-до» за м² по 5 обобщённым
категориям материала. Компания закупает не плитку, а целые слэбы
фиксированного размера у одного поставщика (veneziastone.com), и
хочет, чтобы калькулятор подбирал под размеры изделия клиента
конкретный физический слэб конкретного камня и считал точную цену
от его реальной стоимости, а не от рыночного диапазона.

Задача вводит два новых независимых компонента (скрапер сайта
поставщика и JSON-пайплайн данных) и полностью меняет логику
`calculate()` в существующем файле.

## Разведка сайта поставщика

Сайт veneziastone.com недоступен для прямого запроса из текущей
среды (TCP-соединение обрывается по таймауту и через WebFetch, и
через curl — DNS резолвится нормально). Пользователь предоставил
сохранённую страницу `delicato-brown-slabs.html`
(`https://veneziastone.com/marble/delicato-brown/slabs/`), на основе
которой сделан весь дальнейший разбор разметки.

Ключевые находки:

1. **Таблицы отдельных слэбов подгружаются на клиенте, не отдаются
   в исходном HTML.** На странице 15 карточек «Партия» (batch), но
   таблица с артикулами (Артикул/Размер/Цена) присутствовала в
   сохранённом HTML только для 3 из 15 — видимо, остальные
   подгружаются по мере скролла/раскрытия панели. Обычный
   `requests`+BeautifulSoup пропустил бы ~80% слэбов. **Скраперу
   нужен headless-браузер (Playwright), который долистывает
   страницу до конца и ждёт подгрузки каждой партии.**
2. **Структура строки слэба** (`tr.pr-tr` внутри `table.pr-table`):
   столбцы Фото · Артикул · Номер пачки · Город · Размер (м, вида
   `2,76 x 1,77`) · Вычет (м²) · Площадь (м², уже за вычетом дефекта)
   · Скидка · Цена за м² · Цена (итого за слэб) · кнопка действия.
   Цена и Цена-за-м² показаны двумя значениями: перечёркнутая
   исходная (`div.price-sale`) и финальная цена со скидкой (обычный
   `div` рядом) — **в данные идёт финальная цена**.
3. **Недоступные слэбы помечены явно**: рядом с артикулом стоит
   статус-спан (`В резерве`, а также встречаются `Продано` и
   `По запросу`), и вместо кнопки «В корзину» стоит кнопка «Заявка».
   `По запросу` означает, что у позиции нет фиксированной цены.
   Строки с любым из статусов `В резерве` / `Продано` / `По запросу`
   (или просто с кнопкой «Заявка» вместо «В корзину», как более
   надёжный резервный признак) **исключаются** из `slabs.json`.
4. **Отдельная секция «В пути»** (партии в дороге, ещё не на складе)
   свёрнута по умолчанию за переключателем `#switch-shipping` —
   скрапер просто не трогает этот переключатель, и такие партии
   никогда не попадают в выгрузку.
5. **Валюта.** Метатег `schema.org/AggregateOffer` на странице
   показывает `priceCurrency: RUB` по умолчанию для этой локали —
   переключать валюту не требуется. **По решению пользователя,
   `fetch_rates.py`/`rates.json` из задачи убираются**: цены
   берутся из данных сайта уже в рублях, конвертация EUR→RUB не
   нужна.
6. **«Вычет, м²»** — небольшая скидка по площади за дефект слэба.
   Для MVP игнорируется (используется полная физическая площадь
   `width_m × length_m`), как решил пользователь.
7. Пользователь подтвердил, что страницы всех камней (гранит, оникс
   и т.д.) построены на одном шаблоне — селекторы переносятся без
   изменений на другие страницы.

## Компоненты

```
D:\calculator\

  scripts\
    scrape_slabs.py             # Playwright-скрапер -> data\slabs.json
    stone_urls.txt              # список страниц камней (по одной на строку, # — комментарий)
  data\
    slabs.json
  SCHEDULING.md                 # инструкция по Task Scheduler
```

### 1. `scripts/scrape_slabs.py`

Python + Playwright (headless Chromium). Для каждого URL из
`stone_urls.txt`:

1. Открыть страницу, дождаться рендера карточек партий.
2. Долистать страницу до конца (или до отсутствия новых партий),
   чтобы клиентский код подгрузил таблицы всех партий.
3. Не трогать переключатель `#switch-shipping` (секция «В пути»
   остаётся скрытой и не парсится).
4. Для каждой строки `tr.pr-tr` в каждой раскрытой таблице:
   - если рядом с артикулом есть статус-спан (`В резерве`, `Продано`,
     `По запросу`) или кнопка «Заявка» вместо «В корзину» —
     пропустить;
   - иначе извлечь артикул, номер пачки, город, размер (см →
     нормализовать `2,76 x 1,77` в сантиметры `276 x 177`),
     финальную цену за м² и финальную цену за слэб.
5. Название камня и `id` — из `<h1>`/заголовка страницы.
6. Результаты **мержатся** в `data/slabs.json` по `id` камня (так
   что скрапинг одного камня не затирает данные по остальным),
   с обновлением `updated_at`.
7. Если на камне не нашлось ни одного доступного слэба — не
   затирать предыдущие данные пустым списком, залогировать
   предупреждение.
8. Флаг `--debug` печатает по каждой партии, сколько строк найдено
   и почему строка была отфильтрована — для ручной проверки, если
   разметка на какой-то странице отличается.

`slabs.json`:

```json
{
  "updated_at": "2026-09-11T10:00:00+03:00",
  "stones": [
    {
      "id": "delicato-brown",
      "name": "Delicato Brown",
      "source_url": "https://veneziastone.com/marble/delicato-brown/slabs/",
      "slabs": [
        {
          "article": "P0444194",
          "party": "13168",
          "pachka": "BLP02316",
          "city": "Санкт-Петербург",
          "width_cm": 276,
          "length_cm": 177,
          "price_per_m2_rub": 11008,
          "price_total_rub": 52673
        }
      ]
    }
  ]
}
```

### 2. Калькулятор — переработка `calculate()`

- При загрузке страницы: `fetch('data/slabs.json')`, заполнение
  выпадающего списка «Материал» динамически из `stones[].name`
  (вместо статичного `MATERIALS`).
- `PRODUCTS` дополняется полем `type: 'A' | 'B'`:
  - **Тип A** (цельный кусок, без шва) — `stoleshnitsa`,
    `podokonnik`, `kamin`, `stupeni`.
  - **Тип B** (площадное, со швами) — `stena`, `fasad`, `lestnitsa`
    (лестница по умолчанию отнесена к типу B для MVP, как отдельный
    подтип с доп. предупреждением — см. ниже).
- Константы (легко менять):
  ```js
  const SAW_MARGIN_CM = 4;       // запас на распил с каждого края
  const AREA_WASTE_FACTOR = 1.3; // на подрезку/подгонку швов и брак (тип B)
  const MARKUP_PERCENT = 0.35;   // наша наценка: обработка + распил + маржа
  ```
- **Тип A**: `need_w = width*100 + 2*SAW_MARGIN_CM`,
  `need_l = length*100 + 2*SAW_MARGIN_CM`. Слэб подходит, если
  `(slab.width_cm≥need_w && slab.length_cm≥need_l) ||
  (slab.width_cm≥need_l && slab.length_cm≥need_w)` (разворот
  разрешён). Среди подходящих берётся самый дешёвый
  (`price_total_rub`). Если ни один слэб не подходит — цена не
  показывается, выводится «Нужно уточнить у менеджера — подходящего
  слэба нет». Остаток = `slab.width_m*slab.length_m − width*length`.
- **Тип B**: `nSlabs = ceil(area*AREA_WASTE_FACTOR / slab_area)` —
  берётся слэб выбранного камня с наименьшей `price_per_m2_rub`.
  Итог = `nSlabs × price_total_rub` этого слэба. Если `nSlabs > 1`
  — предупреждение «Потребуется N слэбов со швом». Строка «остаток»
  не показывается (нет одного цельного остатка).
- **`lestnitsa` — доп. предупреждение**: после расчёта по формуле
  типа B дополнительно показывается блок «Точный расчёт лестницы
  требует уточнения количества и размера ступеней у менеджера», и
  цена визуально подаётся с меньшей уверенностью (не как точная
  цифра для стены — отдельный стиль/иконка предупреждения).
- **Наценка**: `итог = subtotal + subtotal × MARKUP_PERCENT ×
  product.complexityMultiplier × (1 + Σ выбранных опций)` — сохраняет
  существующие `complexityMultiplier` и `OPTION_SURCHARGE`.
- **Отображение результата**: точная цифра (не диапазон) +
  мелким текстом: «Расчёт по ценам на [дата из `updated_at`],
  точная цена подтверждается менеджером».
- **Информационный блок** (всегда, кроме случая «нет слэба»):
  «Стоимость указана за весь слэб — остаток после раскроя бесплатно
  хранится на складе компании, клиент может использовать его для
  другого проекта или забрать себе.» + строка «Остаток: X м²» только
  для типа A.

### 3. Планирование (Windows Task Scheduler)

Только один скрипт теперь нужно шедулить (`scrape_slabs.py`,
`fetch_rates.py` убран). Пример регистрации ежедневного запуска:

```powershell
schtasks /create /tn "VeneziaStone-ScrapeSlabs" /tr "python D:\calculator\scripts\scrape_slabs.py" /sc daily /st 07:00 /f
```

`SCHEDULING.md` объяснит это плюс альтернативу через Task Scheduler
GUI, и явно отметит допущение: скрипт запускается на той же машине,
что раздаёт `data/slabs.json` калькулятору (как именно данные
попадают на веб-сервер компании — вне рамок этой задачи, если нужен
отдельный шаг деплоя, дайте знать).

## Открытые допущения (проверить после первого реального прогона)

- Разметка всех страниц камней идентична `delicato-brown` (по
  словам пользователя — да).
- Только `delicato-brown` в `stone_urls.txt` на старте; остальные
  камни пользователь добавит сам.
- `lestnitsa` отнесена к типу B — можно поменять, если на практике
  лестницы считаются иначе.
