# Дизайн: бортик/фартук/остров как отдельные позиции столешницы

Дата: 2026-09-17

## Контекст и цель

При проверке новой формулы ценообразования (см.
`docs/superpowers/specs/2026-09-17-work-cost-pricing-redesign-design.md`)
на реальном КП по столешнице Tundra Grey (мрамор, площадь 5.32 м²)
обнаружилось, что реальное «изготовление» в КП (135 300 ₽) включает
бортик и полуостров, которых калькулятор не считает вообще — сравнение
калькулятора с этим отчётом получилось не яблоки-к-яблокам.

Это прямое следствие пропуска: ещё на этапе брейнсторминга формулы
работы было решено, что бортик/плинтус/фартук/остров должны стать
«опциями внутри столешницы» со своей ₽/м² или ₽/м.п. ставкой — но при
проектировании итоговой формулы это решение не попало в спеку: «остров»
по ошибке превратился в множитель «сложная форма» на изготовление, а
бортик и фартук не появились нигде. Эта задача реализует то, что было
решено изначально.

## Состав позиций и единицы измерения

- **Бортик/плинтус** — ₽ за погонный метр (м.п.).
- **Фартук** — ₽ за м².
- **Остров/полуостров** — ₽ за м².

«Сложная форма» (`COMPLEX_SHAPE_MULTIPLIER`) остаётся отдельным,
самостоятельным множителем на `fabrication` — он про сложные вырезы и
фигурный рез вообще, не только про остров. Остров/полуостров больше не
подразумевает автоматическое включение этого множителя.

## Формула

```
extras = bortikLengthM * (rates.bortikRatePerM ?? 0)
       + fartukAreaM2   * (rates.fartukRatePerM2 ?? 0)
       + ostrovAreaM2   * (rates.ostrovRatePerM2 ?? 0)

work  = fabrication + installation + polish + misc + extras
total = subtotal + work
```

`bortikLengthM`/`fartukAreaM2`/`ostrovAreaM2` по умолчанию `0` (позиция
не введена клиентом — не участвует в цене). Как и с `MISC_FLAT_SUM`,
`null`-ставка трактуется как 0 — цена не считается «на глаз», позиция
просто пока не влияет на итог, пока по ней нет реальных данных.

## Ставки: null до появления чистых данных

Как и `MISC_FLAT_SUM`/`MISC_RATE_PER_M2`, ставки для бортика/фартука/
острова остаются `null` (не грубая оценка) — ни в одном из 7 разобранных
КП эти позиции не выделены отдельной строкой от базовой стоимости
столешницы (в Tundra Grey бортик+остров учтены одной суммой внутри
«изготовления»). Подставлять оценочное число значило бы повторить ту же
ошибку, которую уже отметили в предупреждении над `WORK_RATES`. Ставки
уточняются, когда появится «чистый» КП с этими позициями, выделенными
отдельной строкой.

```js
// Ставки для доп. позиций столешницы (бортик/фартук/остров). Ни один из
// 7 разобранных КП не даёт эти суммы отдельной строкой от базовой
// столешницы (в Tundra Grey бортик+остров учтены одной суммой внутри
// "изготовления" — 135300 ₽ на 5.32 м², что уже превышает ставку
// столешницы 37500 ₽/м² почти вдвое, если считать всё как одну
// столешницу). ТРЕБУЕТ ЗАПОЛНЕНИЯ реальными данными, когда появится
// КП с этими позициями, выделенными отдельно.
const COUNTERTOP_EXTRAS_RATES = {
  bortikRatePerM: null,
  fartukRatePerM2: null,
  ostrovRatePerM2: null
};
```

## Область применения

Новые поля ввода и позиции формулы актуальны только для
`stoleshnitsa_kuhnya`/`stoleshnitsa_vannaya` — для пола, лестниц,
фасадов и т.д. бортик/фартук/остров не имеют смысла. Отмечается новым
булевым полем на записи в `PRODUCTS`:

```js
stoleshnitsa_vannaya: { label: "Столешницы в ванную", type: 'A', supportsCountertopExtras: true },
stoleshnitsa_kuhnya:  { label: "Столешницы на кухню", type: 'A', supportsCountertopExtras: true },
```

Остальные записи `PRODUCTS` это поле не получают (не `false` — просто
отсутствует, как уже сделано с `allowSeam`).

## Интерфейс `pricing.js` (расширение, не breaking change для существующих вызовов)

`computeWorkAndTotal(subtotal, area, rates, options, extraDimensions)` —
пятый параметр, необязательный:

```js
extraDimensions = { bortikLengthM: 0, fartukAreaM2: 0, ostrovAreaM2: 0 }
```

При отсутствии параметра (все существующие вызовы в тестах и в
`calculatePrice` для продуктов без `supportsCountertopExtras`) значения
по умолчанию дают `extras = 0` — старое поведение не меняется, только
добавляется. Возвращаемое значение получает новое поле `extras`.

`calculatePrice(params)` получает новый необязательный параметр
`extraDimensions` с теми же тремя полями и default-значениями по 0,
передаёт его в `computeWorkAndTotal` во всех трёх местах вызова (Type A
одна плита, Type A с швом, Type B), и включает `extras` в возвращаемый
объект (`empty` тоже получает `extras: null` для веток `ok:false`, по
аналогии с остальными компонентами).

`rates`, приходящий из HTML, получает три новых поля
(`bortikRatePerM`, `fartukRatePerM2`, `ostrovRatePerM2`) — для типов без
`supportsCountertopExtras` они просто не используются (extraDimensions
всегда нулевые для них).

## UI (`sayanmramor-calculator.html`)

Три новых числовых поля под текущим блоком чек-боксов (после блока
`.checkboxes`, строки ~549-559):

```html
<div class="field" id="countertopExtras" style="display:none">
  <label>Дополнительные позиции</label>
  <div class="dims">
    <input type="number" id="extra-bortik" placeholder="Бортик, м.п." min="0" step="0.01">
    <input type="number" id="extra-fartuk" placeholder="Фартук, м²" min="0" step="0.01">
    <input type="number" id="extra-ostrov" placeholder="Остров/полуостров, м²" min="0" step="0.01">
  </div>
</div>
```

Видимость блока (`display`) переключается там же, где сейчас
устанавливается `selectedProductKey` при выборе изделия в сетке — по
`product.supportsCountertopExtras`.

При расчёте (там же, где сейчас читаются чек-боксы, строки ~877-893):
значения читаются через `parseFloat(...) || 0` (пустая строка/не число
→ 0), и если для текущего продукта `supportsCountertopExtras` не
установлен — `extraDimensions` принудительно нулевые независимо от
того, что осталось в полях от предыдущего выбора (защита от «прилипшего»
значения при переключении между типами изделия).

`rates` дополняется тремя полями из `COUNTERTOP_EXTRAS_RATES`. Строка
`Опции:` под ценой получает дополнительные пункты для введённых
значений (например «Бортик: 3.2 м.п.», «Фартук: 1.1 м²») — по аналогии
с текущим списком выбранных чек-боксов, без указания рублей по каждой
позиции (разбивка стоимости в рублях по-прежнему не показывается
клиенту — решение уже принято и не пересматривается в этой задаче).

## Тесты

`tests/pricing.test.js`: новые тесты на `computeWorkAndTotal` с
`extraDimensions` (все три позиции по отдельности и вместе, нулевые
ставки/`null`-ставки дают `extras: 0`), плюс проверка, что существующие
вызовы без пятого параметра продолжают работать как раньше (не ломает
обратную совместимость).

`tests/product-types.test.js`: `COUNTERTOP_EXTRAS_RATES` содержит ровно
три поля, все `null`; `supportsCountertopExtras: true` стоит ровно на
`stoleshnitsa_kuhnya`/`stoleshnitsa_vannaya` и ни на одном другом типе.

## Не входит в эту задачу

- Конкретные числовые ставки для бортика/фартука/острова — ждут
  «чистого» КП с этими позициями, выделенными отдельной строкой.
- Пересчёт `fabricationRatePerM2`/`installationRatePerM2` для
  `stoleshnitsa_kuhnya`/`stoleshnitsa_vannaya` (37 500/17 500) — по
  итогам обсуждения Tundra Grey это отдельная задача, требующая
  «чистого» отчёта без доп. позиций, не блокируется этой задачей и не
  решается здесь.
- Показ разбивки стоимости по рублям в UI клиенту — решение уже
  отложено ранее и не пересматривается.
