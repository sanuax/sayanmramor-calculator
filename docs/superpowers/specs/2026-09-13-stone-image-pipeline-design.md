# Дизайн: пайплайн картинок камней + отслеживание "нет в наличии"

Дата: 2026-09-13

## Контекст и цель

Пользователь хочет переделать выбор материала в калькуляторе в стиле
пикера подарков в Telegram (поиск, сетка карточек с картинкой, лайтбокс,
фильтр по твёрдости, сортировка, ленивая подгрузка). Эта задача разбита
на два независимых шага:

- **Шаг A (этот документ)** — слой данных: у каждого камня в
  `data/slabs.json` должна появиться картинка текстуры, а камни без
  доступных слэбов должны сохраняться в файле (а не исчезать из него),
  чтобы UI мог явно показать "нет в наличии".
- **Шаг B (отдельная спека позже)** — сам UI-пикер, потребляющий данные
  из шага A. Не рассматривается в этом документе.

Без шага A шаг B нереализуем: сейчас `data/slabs.json` не содержит
картинок вообще, а камень с нулём слэбов при скрапинге просто
пропускается (см. находку ниже) — то есть "нет в наличии" физически
не может существовать как состояние в данных.

## Текущее поведение (находка)

`merge_stone_into_data` в `scripts/scrape_slabs.py`:

```python
def merge_stone_into_data(data, stone):
    if not stone.get('slabs'):
        return data, True
    ...
```

Если у камня 0 доступных слэбов, функция возвращает **исходные данные
без изменений** и флаг `True` (сейчас используется только для лога
`WARNING: no available slabs found`). Для camня, которого раньше не
было в файле, это означает, что он никогда не появится в
`data/slabs.json`, пока хоть раз не наберёт ≥1 доступный слэб.

## Решения

1. **Пустые камни сохраняются.** Убираем ранний `return` — камень с
   `slabs: []` всегда попадает в файл (новый или существующий).
2. **Картинки — локально, не хотлинк.** Скачиваем и храним на той же
   машине, что раздаёт `data/slabs.json` (см. `SCHEDULING.md` — уже
   предполагается, что это одна машина). Причины: veneziastone.com в
   этой же сессии несколько раз отдавал `ERR_TIMED_OUT`/таймауты на
   уже ранее рабочих URL — не полагаемся на его постоянную
   доступность как на CDN для собственного калькулятора; так же нет
   риска hotlink-защиты.
3. **Логика парсинга картинки — внутри `scrape_slabs.py`.** Страница
   камня и так открывается для парсинга цен; извлечение URL картинки
   переиспользует уже загруженный HTML, не требует второго прохода
   браузером по тем же URL.
4. **Каденция обновления картинок реже, чем цены — через флаг
   `--fetch-images`, а не отдельный скрипт.** Один и тот же
   `scrape_slabs.py`:
   - без флага (ежедневный прогон, как сейчас) — только цены;
     `image` для каждого камня переносится вперёд из предыдущих
     данных без изменений;
   - с флагом `--fetch-images` (отдельная задача Task Scheduler раз в
     неделю/месяц) — при проходе по каждому камню дополнительно
     скачивает картинку.

## Данные

Новое поле `image` на каждом камне:

```json
{
  "id": "delicato-brown",
  "name": "Delicato Brown",
  "category": "marble",
  "hardness_category": 1,
  "source_url": "...",
  "image": "images/delicato-brown.jpg",
  "slabs": [...]
}
```

`image` — путь относительно `data/`, или `null`, если картинка ещё
не была скачана ни разу. Файлы лежат в `data/images/`, добавленной в
`.gitignore` рядом с `data/slabs.json` (генерируемые данные, не под
git).

## `merge_stone_into_data`: перенос `image` вперёд

Обычный (ежедневный) прогон не вызывает код скачивания картинки, а
значит объект `stone`, который парсится из HTML, никогда не содержит
ключа `image`. Если сливать его в данные "как есть" поверх
существующей записи, поле `image` у уже известных камней будет
затираться на `None` каждый день. Слияние должно явно переносить
`image` из существующей записи, если новый `stone` его не задаёт:

```python
def merge_stone_into_data(data, stone):
    stones = data.get('stones', [])
    new_stones = []
    updated = False
    was_empty = not stone.get('slabs')
    for existing in stones:
        if existing.get('id') == stone['id']:
            if 'image' not in stone:
                stone['image'] = existing.get('image')
            new_stones.append(stone)
            updated = True
        else:
            new_stones.append(existing)
    if not updated:
        stone.setdefault('image', None)
        new_stones.append(stone)

    new_data = dict(data)
    new_data['stones'] = new_stones
    return new_data, was_empty
```

(Точная реализация уточняется на этапе кода; здесь фиксируется
поведение, не финальный диф.)

## Извлечение URL картинки

`extract_slabs_from_html` дополнительно возвращает URL главной
картинки со страницы (не расходует лишних запросов — HTML уже
загружен):

1. Приоритет — `<meta property="og:image" content="...">`: это
   кросс-сайтовый стандарт, не завязанный на конкретную вёрстку
   карточки товара, и поэтому устойчивее к возможным различиям
   разметки между категориями (мы уже видели на этом сайте, что
   разные категории товаров вёрстаны неодинаково — см. историю с
   `stone_name_from_h1`).
2. Фолбэк — первый `<img>` в основном блоке товара, если `og:image`
   отсутствует.

Точный CSS-селектор для фолбэка нужно будет уточнить по живой
странице сайта на этапе реализации (сеть недоступна прямо сейчас в
этой сессии) — это техническая деталь реализации, не архитектурное
решение.

## Скачивание картинки (`--fetch-images`)

Порядок операций на камень (только когда флаг передан):

1. Скачать картинку по извлечённому URL **во временный файл/буфер**.
2. **Если скачивание успешно** — удалить любые существующие файлы
   `data/images/<stone_id>.*` (с любым расширением) для этого камня,
   затем сохранить новый файл под именем
   `data/images/<stone_id>.<ext>` (расширение определяется по
   Content-Type ответа). Обновить `stone['image']`.
3. **Если скачивание падает** (сеть, таймаут, 404) — ничего не
   удалять и не перезаписывать; `stone['image']` остаётся прежним.

Такой порядок (скачать → затем заменить) гарантирует, что неудачная
попытка обновления никогда не оставляет камень без картинки, а
удаление старых файлов по маске `<stone_id>.*` перед записью новой
гарантирует отсутствие мусорных файлов на диске при смене расширения
между обновлениями (например, `.jpg` → `.webp`).

## Обработка ошибок

Скачивание картинки — дополнительный шаг **после** уже успешного
парсинга цен для камня; его падение не должно ронять весь прогон и не
должно откатывать уже распарсенные цены/слэбы этого камня для текущего
запуска. Ошибка логируется в stderr в том же стиле, что и существующий
`ERROR scraping` (см. `scripts/scrape_slabs.py:363`).

## Изменения в `SCHEDULING.md`

Добавляется вторая задача Task Scheduler:

```
schtasks /create /tn "VeneziaStone-ScrapeSlabsImages" /tr "python D:\calculator\scripts\scrape_slabs.py --fetch-images" /sc weekly /d SUN /st 07:00 /f
```

(частота — раз в неделю; можно сделать `/sc monthly`, если картинки
меняются ещё реже — решается на усмотрение пользователя при
развёртывании, не блокирует реализацию).

## Тестирование

Юнит-тесты на фикстуре (как остальная логика в
`tests/test_scrape_slabs.py`):

- извлечение `og:image` из HTML;
- фолбэк на `<img>`, когда `og:image` отсутствует;
- `merge_stone_into_data` сохраняет камень с `slabs: []` вместо того,
  чтобы пропускать его;
- `merge_stone_into_data` переносит `image` вперёд из существующей
  записи, когда новый `stone` не задаёт этот ключ;
- новый камень без `image` получает `image: None`, а не отсутствие
  ключа.

Сетевое скачивание файла (`--fetch-images`) не гоняется по-настоящему
в юнит-тестах — HTTP-слой мокается; проверяется только: успешный путь
пишет файл и обновляет `stone['image']`, неудачный путь не трогает ни
файл, ни поле, логика "удалить старые расширения перед записью новой"
проверяется на замоканной файловой системе/tmp-директории.

## Вне рамок этого документа

- Сам UI-пикер (Шаг B) — поиск, сетка, лайтбокс, фильтр по твёрдости,
  сортировка, ленивая подгрузка. Будет забрифован отдельно, когда
  Шаг A реализован.
- Ресайз/сжатие картинок (thumbnails) — не требуется для MVP; при
  необходимости добавляется позже, когда станет понятен реальный вес
  страницы с картинками.
- Точный CSS-селектор фолбэка для картинки — уточняется на этапе
  реализации по живому сайту.
