# Дизайн: пересчёт стоимости работ (изготовление/монтаж/полировка/прочее) по реальным КП

Дата: 2026-09-17

## Контекст и цель

Текущая формула в `pricing.js`/`product-types.js`:

```
work  = subtotal × workMultiplier × complexityMultiplier × (1 + Σ опций)
total = subtotal + work
```

где `subtotal` — стоимость подобранного камня, `workMultiplier` берётся
из `HARDNESS_WORK_MULTIPLIER[hardness_category]` (или `WORK_MULTIPLIER`
по умолчанию), `complexityMultiplier` — константа на тип изделия, а
опции (`complex`/`polish`/`install`) добавляют проценты к сумме.

Пользователь разобрал 11 реальных коммерческих предложений (7 из них —
чистые, с явной построчной разбивкой камень/изготовление/монтаж/
прочее) и обнаружил, что соотношение (работа+монтаж+прочее) / камень
колеблется от 1.22× до 6.4× по этим 7 КП. Это не шум измерения: в
самих КП изготовление и монтаж указаны как **фиксированная ставка за
м² (или за м.п.)**, которая почти не зависит от цены камня, а зависит
от типа изделия и сложности конкретных операций (вырезы, поры камня,
углы). Формула «камень × множитель» структурно не может воспроизвести
такое поведение — она всегда пропорциональна цене камня, а реальность
устроена наоборот.

Цель этой задачи — заменить формулу работы на аддитивную модель по
компонентам (ставка ₽/м² × площадь), опираясь на реальные ставки из
разобранных КП там, где они есть, и на явно помеченные оценки — там,
где данных пока нет. Подбор слэбов и расчёт `subtotal` (геометрия,
`findBestTypeASlab`, `computeTypeBResult`, `minCostCover`) в этой
задаче не меняются.

## Данные из КП (источник ставок)

| Тип изделия | Изготовление ₽/м² | Монтаж ₽/м² | Полировка ₽/м² | Статус |
|---|---|---|---|---|
| Столешница (мрамор/гранит/агломерат/травертин, разные КП) | 30 000–65 000 (варьируется по камню/сложности выреза, единой зависимости от твёрдости не найдено) | 15 000–25 000 | нет отдельных данных | реальные |
| Пол (без герба) | 3 600 | 9 600 | 18 000 | реальные (КП «панно-герб», обычный пол) |
| Стены (санузел) | нет отдельной позиции — была одна общая «изготовление санузла» | 25 000 (вместе с полировкой в одной позиции: монтаж+переполировка = 45 000) | 20 000 | частично реальные |
| Панно (герб, гидроабразивная резка) | 510 000 | — | — | реальное, но это крайний случай сложности, не типовая ставка — фиксируется как пример верхней границы в комментарии, не как рабочая ставка |
| Лестницы, фасады, ступени, подоконники | — | — | — | нет данных |

Разброс 1.22×–6.4× по 7 КП объясняется тем, что дешёвый камень со
сложной обработкой (травертин с порами, остров с вырезом под мойку)
даёт высокий множитель, а дорогой камень с простой обработкой
(Calacatta Viola, простой остров) — низкий, потому что работа считается
от площади и типа операции, а не от цены камня.

## Формула

```
area = widthM × lengthM   // м² изделия (не площадь подобранного слэба)

fabrication  = FABRICATION_RATE[type] × (complexEnabled ? COMPLEX_SHAPE_MULTIPLIER : 1) × area
installation = installEnabled ? INSTALLATION_RATE[type] × area : 0
polish       = polishEnabled  ? POLISH_RATE[type] × area : 0
misc         = MISC_FLAT_SUM + MISC_RATE_PER_M2 × area

work  = fabrication + installation + polish + misc
total = subtotal + work
```

`subtotal` вычисляется как и сейчас, до этой формулы. `area` — новый
параметр, которого раньше не было в `computeWorkAndTotal` (раньше
work считался только из `subtotal`); для типа A он не совпадает с
площадью подобранного слэба и должен браться из `widthM × lengthM`,
переданных в `calculatePrice`.

### "Прочее" — два компонента, не один

Разбор реальных КП показывает, что «прочее» неоднородно:

- **Замер** — фиксированная сумма за выезд, не зависит от площади.
- **Доставка** — фиксированная ставка за рейс (число рейсов может расти
  для очень крупных заказов, но это для калькулятора не моделируем —
  берём один рейс).
- **Расходный материал** — явная ставка ₽/м², растёт с площадью.
- **Разгрузка** — явная ставка ₽/кг, растёт с объёмом/весом — для
  калькулятора приближаем через ₽/м², так как веса слэбов калькулятору
  не известны.

Отсюда два раздельных компонента вместо одной усреднённой константы:
`MISC_FLAT_SUM` (замер + один рейс доставки) и `MISC_RATE_PER_M2`
(расходники + разгрузка, приближённо).

### Опции UI меняют смысл

- **«Сложная форма»** — раньше `+25%` к `subtotal+work`. Данные по
  острову с вырезом под мойку/варочную панель (35 000 → 95 000 ₽/м²)
  показывают, что сложность двигает саму ставку изготовления, а не
  добавляет процент к готовой сумме. Новая реализация:
  `COMPLEX_SHAPE_MULTIPLIER` применяется только к `fabrication`.
  Единого источника точного значения нет (одно наблюдение по одному
  проекту) — берём умеренную оценку (например ×1.5) с явной пометкой
  "оценка по одному наблюдению, требует уточнения".
- **«Полировка»** — раньше `+10%`. Реальные данные (пол, стены) дают
  ставку 18 000–20 000 ₽/м², то есть это давно не 10% от суммы, а
  самостоятельный дорогой компонент. Меняется на компонент `polish` —
  включатель ₽/м²-ставки, а не процентная надбавка.
- **«Монтаж»** — раньше `+15%`. Теперь монтаж — базовый компонент
  формулы (`installation`), а не бонус сверху. Чек-бокс превращается в
  переключатель "нужен ли монтаж" (выключен = самовывоз, клиент
  устанавливает сам и не платит за этот компонент).

`OPTION_SURCHARGE` (объект с процентами) удаляется целиком.

## Таблица ставок (заменяет `WORK_MULTIPLIER`, `HARDNESS_WORK_MULTIPLIER`, `complexityMultiplier`)

`complexityMultiplier` как рантайм-параметр пропадает из `PRODUCTS`.
Он использовался только для скейлинга формулы работы — при новой
модели ставки для типов без собственных данных считаются один раз при
заполнении таблицы (ставка столешницы × текущий `complexityMultiplier`
этого типа) и записываются как обычное число с комментарием "оценка".
Рантайм-движок ценообразования работает с одной плоской таблицей, без
двух параллельных формул внутри `pricing.js`.

Каждое поле в новой таблице ставок в `product-types.js` должно быть
явно помечено комментарием: основано на реальном КП или это временная
оценка (это важно для пользователя — чтобы не забыть, что уточнить,
когда появятся новые заказы). Пример структуры (числа ориентировочные,
финализируются при реализации по факту разбора всех 7 КП):

```js
const WORK_RATES = {
  // РЕАЛЬНЫЕ КП: столешницы кухня/ванная/остров. Диапазон по 7 КП —
  // изготовление 30 000-65 000/м² (варьируется по камню и сложности
  // выреза, единой зависимости от hardness_category не найдено —
  // травертин, category 1, дал одну из самых высоких ставок из-за пор
  // в камне, а не из-за твёрдости). Взято усреднённое значение по
  // решению пользователя (без разбивки по материалу) —
  // ТРЕБУЕТ УТОЧНЕНИЯ, когда будут разобраны оставшиеся 3-4 КП.
  stoleshnitsa_kuhnya:  { fabricationRatePerM2: 37500, installationRatePerM2: 17500, polishRatePerM2: 18000 /* нет своих данных, оценка по аналогии с полом/стенами */ },
  stoleshnitsa_vannaya: { fabricationRatePerM2: 37500, installationRatePerM2: 17500, polishRatePerM2: 18000 /* тот же источник и та же оговорка */ },

  // РЕАЛЬНЫЕ КП: обычный пол без герба (КП «панно-герб»).
  pol: { fabricationRatePerM2: 3600, installationRatePerM2: 9600, polishRatePerM2: 18000 },

  // ЧАСТИЧНО РЕАЛЬНЫЕ: санузел. installationRatePerM2/polishRatePerM2 —
  // из КП (монтаж+переполировка = 45000, разложено 25000/20000).
  // fabricationRatePerM2 — ОЦЕНКА (столешница × текущий complexityMultiplier
  // типа "stena" = 1.1), в КП изготовление стен санузла шло одной общей
  // позицией без разбивки.
  stena: { fabricationRatePerM2: 41250 /* оценка: 37500 × 1.1 */, installationRatePerM2: 25000, polishRatePerM2: 20000 },

  // ОЦЕНКА целиком (столешница × текущий complexityMultiplier типа "panno" = 1.6).
  // Реальный КП по панно есть, но это крайний случай (гидроабразивная
  // резка герба) — НЕ берём как типовую ставку, фиксируем отдельно как
  // пример верхней границы сложности:
  // panno_extreme_example_rub_per_m2 = 510000 (герб, гидроабразивная резка)
  panno: { fabricationRatePerM2: 60000 /* 37500 × 1.6 */, installationRatePerM2: 28000 /* 17500 × 1.6 */, polishRatePerM2: 28800 /* 18000 × 1.6 */ },

  // ОЦЕНКА ЦЕЛИКОМ, данных нет вообще — столешница × текущий complexityMultiplier типа.
  lestnitsa:  { fabricationRatePerM2: 67500 /* × 1.8 */, installationRatePerM2: 31500 /* × 1.8 */, polishRatePerM2: 32400 /* × 1.8 */ },
  fasad:      { fabricationRatePerM2: 48750 /* × 1.3 */, installationRatePerM2: 22750 /* × 1.3 */, polishRatePerM2: 23400 /* × 1.3 */ },
  stupeni:    { fabricationRatePerM2: 52500 /* × 1.4 */, installationRatePerM2: 24500 /* × 1.4 */, polishRatePerM2: 25200 /* × 1.4 */ },
  podokonnik: { fabricationRatePerM2: 30000 /* × 0.8 */, installationRatePerM2: 14000 /* × 0.8 */, polishRatePerM2: 14400 /* × 0.8 */ },
};

// ТРЕБУЕТ ДАННЫХ — ни один из 7 разобранных КП не даёт построчную
// сумму именно "прочего" (замер/доставка/расходники/разгрузка) в
// отрыве от камня и работы. Известно только, что "прочее" — 15-25% от
// общей суммы КП, и что оно неоднородно (замер/один рейс доставки —
// фиксированная часть; расходники/разгрузка — растущая с площадью
// часть). Финализируется в implementation-плане после разбора
// оставшихся 3-4 КП или по числам, которые пользователь предоставит
// отдельно.
const MISC_FLAT_SUM = null;      // TODO: замер + один рейс доставки
const MISC_RATE_PER_M2 = null;   // TODO: расходники + разгрузка (приближённо)

// ОЦЕНКА по одному наблюдению: остров с вырезом под мойку/варочную
// панель — 35 000 → 95 000 ₽/м² изготовление (≈×2.7), но это самый
// сложный из виденных случаев, а не типичная "сложная форма". Берём
// более умеренную оценку до появления второго наблюдения.
const COMPLEX_SHAPE_MULTIPLIER = 1.5;
```

`stone.hardness_category` перестаёт использоваться ценообразованием
(поле остаётся в данных камня — оно уже отмечено как нужное для
будущей фильтрации камня для кухонных столешниц, см. TODO в
`product-types.js`, но это отдельная задача).

## Интерфейс `pricing.js` (breaking change)

Старая сигнатура:

```js
Pricing.calculatePrice({
  stone, widthM, lengthM, productType, complexityMultiplier,
  optionSurchargeSum, marginCm, wasteFactor, workMultiplier, allowSeam
})
// -> { ok, subtotal, work, total, ... }
```

Новая:

```js
Pricing.calculatePrice({
  stone, widthM, lengthM, productType, marginCm, wasteFactor, allowSeam,
  rates: {
    fabricationRatePerM2, installationRatePerM2, polishRatePerM2,
    miscFlatSum, miscRatePerM2, complexShapeMultiplier
  },
  installEnabled, polishEnabled, complexEnabled
})
// -> { ok, subtotal, fabrication, installation, polish, misc, work, total, ... }
```

`computeWorkAndTotal(subtotal, area, rates, options)` возвращает разбивку
по компонентам (`fabrication`, `installation`, `polish`, `misc`, `work`,
`total`), а не только `work`/`total` — это ничего не стоит и даёт
задел на будущее (например, если позже понадобится показать разбивку
в UI — вопрос отложен пользователем на отдельное обсуждение и в этой
задаче не решается).

`sayanmramor-calculator.html` (строки ~877-904) собирает `rates` из
`WORK_RATES[selectedProductKey]` и три булевых флага из чек-боксов
вместо текущего накопления `multiplier`/`surchargeLabel` через проценты
`OPTION_SURCHARGE`.

### Кросс-репозиторный риск: sayanmramor-site

`pricing.js` уже используется вторым потребителем — каркасом нового
сайта-каталога `sayanmramor-site`, который живёт в **отдельном
репозитории** (не в `D:\calculator`) и уже реально вызывает
`Pricing.calculatePrice` со старой сигнатурой
(`complexityMultiplier`/`optionSurchargeSum`/`workMultiplier`). Эта
задача не может сама найти и поправить те вызовы — нужна ручная
координация вне этого репозитория. Implementation-план должен явно
включать шаг «после мержа этой задачи — обновить вызов
`calculatePrice` в `sayanmramor-site` под новую сигнатуру», иначе тот
сайт молча сломается (получит `undefined` в местах, где ждёт старые
параметры) при следующем обновлении `pricing.js`.

## Тесты

`tests/pricing.test.js` вызывает `calculatePrice` с
`complexityMultiplier`/`workMultiplier`/`optionSurchargeSum` почти в
каждом тесте — сигнатура меняется, поэтому эти вызовы придётся
переписать под новые параметры (`rates`, `installEnabled` и т.д.). Это
техническая правка вызовов, а не сокращение покрытия: каждый
существующий тест-кейс (геометрия Type A с одним слэбом, сегментация
со швом, `minCostCover`, Type B по площади, все ветки `reason` —
`no_slabs_for_stone`, `no_priced_slab`, `insufficient_stock`,
`no_fitting_slab`, `invalid_dimensions`) должен сохраниться и пройти
под новой формулой. Добавляются новые тесты на саму формулу работы:
`fabrication`/`installation`/`polish`/`misc` считаются верно по
компонентам, `complexEnabled` умножает только `fabrication`,
`installEnabled`/`polishEnabled` включают/выключают свои компоненты
независимо друг от друга.

## Не входит в эту задачу

- Точные числовые ставки для всех 7 КП — при реализации потребуется
  построчно разобрать оставшиеся 3-4 КП со «грязной» структурой (после
  OCR/извлечения из PDF), которые пользователь предложил прислать
  файлами отдельно.
- Конкретные значения `MISC_FLAT_SUM`/`MISC_RATE_PER_M2` — ни один из
  7 разобранных КП не даёт построчную сумму "прочего" отдельно от
  камня и работы (известно только, что это 15-25% от общей суммы КП
  и что оно неоднородно). До получения точных цифр в реализации эти
  константы должны оставаться явным `TODO`/placeholder, а не
  случайной оценкой "на глаз" — это финансовая величина, которую
  нельзя правдоподобно угадать без данных.
- Разбивка цены по компонентам в UI для клиента — отложено пользователем.
- Зависимость ставок от категории твёрдости/материала камня — данных
  недостаточно (7 чистых КП), решили не закладывать сейчас.
- Фильтрация камня для кухонных столешниц по устойчивости к мех./хим.
  воздействиям — существующий TODO в `product-types.js`, не связан с
  этой задачей.
- Правка вызова `calculatePrice` внутри репозитория `sayanmramor-site` —
  этот план может только зафиксировать риск и дать чек-пункт "обновить
  после мержа", саму правку в чужом репозитории выполняет пользователь
  или отдельная задача там.
